# MindUnlock — سند جامع محصول، معماری و نقشه توسعه

> وضعیت: راهنمای محصول و توسعه (Proposal / Planned). موارد این سند به معنی پیاده‌سازی‌شدن قابلیت‌ها نیستند؛ وضعیت هر قابلیت باید با کد، تست و نسخه واقعی تطبیق داده شود.
>
> هدف: تبدیل MindUnlock به ابزار شخصیِ آفلاین‌محور برای یادگیری، مدیریت ذهن، دانش و کارهای روزانه؛ با معماری‌ای که از ابتدا امکان توسعه و انتشار عمومی در آینده را داشته باشد.

## 1. چشم‌انداز و اصول محصول

MindUnlock ابتدا برای استفاده شخصی ساخته می‌شود؛ اما تصمیم‌های معماری نباید مانع انتشار عمومی در آینده شوند.

اصول:
- Local-first و Offline-first: قابلیت‌های اصلی بدون اینترنت و حساب کاربری کار کنند.
- Privacy by design: افکار، یادداشت‌ها، برنامه‌ها و داده‌های شخصی خصوصی و محلی بمانند.
- Personal first, public-ready: در نسخه شخصی، سرور و ثبت‌نام اجباری نسازیم؛ مرزهای معماری برای چندکاربره‌شدن آینده حفظ شوند.
- Modular: ماژول‌ها وابستگی حداقلی و API داخلی روشن داشته باشند.
- قابل آزمون و نگهداری: منطق کسب‌وکار از UI و زیرساخت جدا باشد.
- فارسی و RTL از ابتدا؛ تاریخ شمسی در نمایش و ورودی‌ها با ذخیره‌سازی استاندارد و قابل تبدیل.
- آموزش تصویرمحور، ساختارمحور، استادمحور، کاربردی و همراه تمرین باشد.
- پروفایل یادگیری قابل ویرایش و مبتنی بر بازخورد واقعی باقی بماند.
- قابلیت برنامه‌ریزی‌شده تا زمان پیاده‌سازی و آزمون، «موجود» تلقی نشود.

## 2. کاربران و مدل انتشار

### نسخه شخصی — اولویت فعلی
- بدون ثبت‌نام و حساب آنلاین
- ذخیره‌سازی محلی
- پشتیبان‌گیری و بازیابی دستی
- تنظیمات و پروفایل یادگیری شخصی
- همگام‌سازی محتوای آموزشی از سرور محلی فقط در صورت نیاز

### آمادگی نسخه عمومی — الزام معماری
- شناسه مستقل برای داده‌های کاربر و مرز مالکیت داده
- قابلیت ایجاد پروفایل محلی مستقل برای هر نصب/کاربر
- لایه Repository و Sync مستقل از UI
- تنظیمات حریم خصوصی، خروجی‌گرفتن و حذف داده
- امکان افزودن احراز هویت و همگام‌سازی ابری در آینده، بدون وابسته‌کردن هسته فعلی به آن‌ها
- چندزبانه‌سازی و تنظیمات منطقه‌ای
- مستندات نصب، راه‌اندازی، بازیابی و سیاست حریم خصوصی

## 3. فناوری و معماری کلان

پایه فعلی مستندشده: Android Native، Kotlin، Jetpack Compose، Room، Retrofit/OkHttp و Coroutines. هر تغییر فناوری باید با ADR ثبت شود.

لایه‌های پیشنهادی:
1. Presentation: صفحات Compose، navigation، state و accessibility.
2. Domain: use caseها، قواعد کسب‌وکار و مدل‌های مستقل از Android.
3. Data: Repositoryها، DAOها، mapperها و منبع داده محلی/شبکه.
4. Core: زمان و تاریخ، تنظیمات، logging، امنیت، جستجو، export/import و ابزارهای مشترک.

ماژول‌های منطقی پیشنهادی:
- :app — نقطه ورود، navigation و تزریق وابستگی‌ها.
- :core:common — نتیجه عملیات، خطاها، dispatcherها و ابزارهای مشترک.
- :core:database — Room، migrationها و database factories.
- :core:designsystem — رنگ، typography، اجزای UI و RTL.
- :core:security — حفاظت از داده و مدیریت کلیدها.
- :core:backup — backup/restore و اعتبارسنجی فایل.
- :core:sync — قرارداد همگام‌سازی و سیاست تعارض.
- :feature:home
- :feature:learning
- :feature:learning-profile
- :feature:inbox
- :feature:tasks
- :feature:journal
- :feature:knowledge
- :feature:review
- :feature:reports
- :feature:settings

این فهرست ساختار هدف است؛ لازم نیست همه ماژول‌ها در یک مرحله ساخته شوند. در پروژه کوچک می‌توان ابتدا packageهای مستقل ایجاد کرد و بعداً آن‌ها را به Gradle module تبدیل کرد.

## 4. مرزبندی داده‌ها و پایگاه‌های اطلاعاتی

دو حوزه داده‌ای باید از نظر مالکیت و مسیر همگام‌سازی جدا باشند:

### Content Database
- دوره‌ها، مسیرها، فصل‌ها، درس‌ها و محتوای آموزشی
- تصاویر، نمودارها، پیوست‌ها و فراداده منابع
- نسخه محتوا، شناسه منبع و اطلاعات همگام‌سازی
- محتوای آزمایشگاه و بانک سؤال عمومی

### User Database
- پروفایل و ترجیحات یادگیری
- پیشرفت، پاسخ‌ها و نقاط ضعف
- Inbox، افکار، کارها، برنامه روزانه و Journal
- یادداشت‌ها، نشانک‌ها و حاشیه‌نویسی‌های شخصی
- برنامه مرور و تاریخچه جلسات

قواعد:
- محتوای آموزشی عمومی نباید باعث ارسال ناخواسته داده‌های شخصی شود.
- مسیر sync محتوا هرگز نباید User Database را بدون قرارداد، مجوز و امنیت مشخص منتقل کند.
- برای داده‌های شخصی، export و حذف کامل باید پیش‌بینی شود.
- برای Room از fallbackToDestructiveMigration در نسخه انتشار استفاده نشود. Migrationهای نسخه‌به‌نسخه، تست مهاجرت و پشتیبان قبل از ارتقا لازم است.
- شناسه‌ها پایدار باشند؛ زمان‌ها به شکل استاندارد ذخیره و در UI به تقویم شمسی تبدیل شوند.
- سیاست حذف منطقی و پاک‌سازی داده باید روشن باشد.

## 5. ماژول خانه (Home / Dashboard)

هدف: نمایش وضعیت امروز و انتخاب قدم بعدی بدون شلوغ‌کردن ذهن.

اجزا:
- تاریخ شمسی و خوشامدگویی ساده
- وضعیت Inbox، کارهای امروز و موضوع یادگیری فعال
- دسترسی سریع به تخلیه ذهن
- نمایش یک قدم بعدی یادگیری
- حداکثر ۳ تا ۴ کار مهم روزانه
- نمایش مرورهای سررسیدشده
- امکان مخفی/مرتب‌سازی کارت‌ها در تنظیمات

صفحه خانه نباید به داشبورد پر از نمودار و اعلان تبدیل شود؛ اولویت با وضوح و کاهش بار شناختی است.

## 6. ماژول تخلیه ذهن و Inbox

هدف: ثبت سریع فکرها و نگرانی‌ها بدون اجبار به دسته‌بندی در لحظه.

قابلیت‌ها:
- ثبت سریع متن، ایده، سؤال، نگرانی، کار یا یادآوری
- ثبت زمان ایجاد و ویرایش
- ورودی کوتاه و بدون فرم طولانی
- برچسب یا دسته اختیاری
- جستجو، فیلتر و آرشیو
- تبدیل هر ورودی به یکی از موارد زیر:
  - Task
  - Learning Topic
  - Future Topic
  - Journal Entry
  - Knowledge Note
  - Processed / Archive
  - Delete
- تعیین زمان بررسی مجدد برای موارد غیرقابل اقدام
- نگه‌داشتن ورودی بدون تصمیم‌گیری فوری

چرخه پیشنهادی:
1. Capture: فقط ثبت.
2. Clarify: مشخص‌کردن منظور، بدون تحلیل اجباری.
3. Decide: اقدام، زمان‌بندی، یادگیری، آرشیو یا حذف.
4. Review: بازبینی موارد باقی‌مانده در زمان مناسب.

افکار جانبی هنگام یادگیری باید به Inbox منتقل شوند تا جلسه آموزشی بی‌دلیل متوقف نشود.

## 7. ماژول مدیریت کارها و برنامه‌ریزی

### Task
فیلدهای پیشنهادی:
- id، title، description
- status: inbox / next / scheduled / in_progress / done / cancelled
- dueAt، scheduledAt، completedAt
- priority اختیاری
- tags، createdAt، updatedAt
- sourceInboxItemId اختیاری
- recurrence اختیاری در نسخه آینده

قابلیت‌ها:
- ثبت، ویرایش، تکمیل، لغو و حذف
- فیلتر امروز، آینده، عقب‌افتاده و انجام‌شده
- مرتب‌سازی بر اساس زمان و اولویت
- تبدیل Inbox به Task
- برنامه روزانه (Daily Plan)
- محدودکردن کارهای مهم روز به ۳ تا ۴ مورد؛ فهرست کامل کارها همچنان قابل دسترس باشد
- نمایش غیرقضاوتی کارهای عقب‌افتاده

### Daily Plan
- تاریخ روز
- ۳ تا ۴ اولویت اصلی
- کارهای زمان‌بندی‌شده
- یادداشت کوتاه روز
- وضعیت پایان روز و انتقال کارهای ناتمام با تأیید کاربر

## 8. ماژول Journal

هدف: ثبت آزادانه اتفاقات، افکار و بازتاب روزانه.

قابلیت‌ها:
- متن آزاد
- تاریخ و زمان
- احساس یا mood اختیاری و غیرتشخیصی
- برچسب و جستجو
- پیوند اختیاری با Task، Learning Topic یا Inbox
- خروجی گرفتن و حذف
- قفل یا حفاظت محلی در صورت نیاز

Journal خصوصی است و نباید به سرور محتوای آموزشی ارسال شود. این ماژول ابزار ثبت شخصی است، نه ابزار تشخیص بالینی.

## 9. موتور یادگیری (Learning Engine)

موتور یادگیری فعلی MindUnlock هسته ارزشمند محصول است و باید حفظ و تثبیت شود.

قابلیت‌های هدف:
- مسیر یادگیری، دوره، فصل و درس
- مطالعه آفلاین پس از دریافت محتوا
- مطالعه مرحله‌ای و ثبت پیشرفت
- مرور، فلش‌کارت، آزمون و آزمایشگاه
- نشانک، یادداشت و حاشیه‌نویسی
- جستجو در محتوا
- دریافت مرحله‌ای محتوا و مدیریت دانلود
- متن‌به‌گفتار فارسی آفلاین در صورت فراهم بودن موتور و مدل مناسب
- مدیریت مدل‌های گفتار به‌صورت دانلود اختیاری، نه قراردادن اجباری همه مدل‌ها در APK
- گزارش پیشرفت و بازگشت به آخرین نقطه مطالعه

### الگوی استاندارد آموزش شخصی
1. چرا این موضوع مهم است و چه مسئله‌ای را حل می‌کند؟
2. نمای کلی و نقشه مفهومی/معماری.
3. توضیح استادمحور، ساده و مرحله‌ای.
4. ارتباط اجزا و وابستگی‌ها.
5. سناریوی واقعی محیط کار.
6. تمرین، آزمایشگاه یا عیب‌یابی.
7. جمع‌بندی با زبان خود یادگیرنده.
8. مرور تصویری و بازیابی از حافظه.

الگوی پیش‌فرض جلسه ۳۰ دقیقه:
- ۱۰ دقیقه آموزش
- ۱۵ دقیقه تمرین
- ۵ دقیقه جمع‌بندی

این زمان قابل تنظیم و کوتاه‌سازی است.

### مدیریت سؤال‌های جانبی
- ضروری برای فهم درس جاری: پاسخ در همان جلسه.
- مفید اما غیرضروری: ثبت برای بررسی بعدی.
- کنجکاوی جانبی: ثبت در Inbox یا فهرست Curiosity.

هدف حفظ کنجکاوی بدون متوقف‌کردن مسیر درس است.

## 10. پروفایل یادگیری (Learning Profile)

آزمون اولیه ۲۰ سؤالی، خوداظهاری است و نباید به‌عنوان تست روان‌شناختی یا برچسب قطعی استفاده شود.

پروفایل اولیه بر اساس پاسخ‌های کاربر:
- تصویرمحور و علاقه‌مند به دیاگرام و نقشه مفهومی
- ساختارمحور؛ ابتدا تصویر کلی و ارتباط اجزا را می‌خواهد
- کاربردمحور؛ سناریوی واقعی و آزمایش برایش مؤثر است
- توضیح استادمحور با مثال را ترجیح می‌دهد
- پس از فهم کلیات، علاقه‌مند به بررسی عمیق جزئیات است
- در جلسه ۳۰ دقیقه‌ای، آموزش/تمرین/جمع‌بندی را ترجیح می‌دهد
- برای یادآوری مفاهیم، اجرای سناریو و مرور تصویری مفید است
- ممکن است مفهوم را حفظ کند ولی دستورات و جزئیات را فراموش کند
- بعد از وقفه، به خلاصه آخرین وضعیت و یک قدم بعدی روشن نیاز دارد
- مشغله ذهنی و مسائل حل‌نشده می‌توانند تمرکز را مختل کنند

### سیاست شخصی‌سازی
- ترتیب ارائه: نمای کلی → دیاگرام → توضیح → مثال واقعی → تمرین → جمع‌بندی → مرور.
- مرور مفاهیم از مرور دستورات و جزئیات جدا باشد.
- برای دستورات، کارت مرور و تمرین بازیابی از حافظه استفاده شود.
- پروفایل قابل ویرایش باشد و ترجیحات خوداظهاری از شاخص‌های عملکرد واقعی جدا ذخیره شوند.
- پس از هر جلسه، بازخورد کوتاه ثبت شود: میزان فهم، دشواری، مفیدبودن تصویر/تمرین و قدم بعدی.
- شخصی‌سازی بر اساس داده کافی و رضایت کاربر انجام شود؛ نتیجه آزمون حقیقت ثابت تلقی نشود.

## 11. ماژول مرور و تثبیت حافظه

قابلیت‌ها:
- مرور فاصله‌دار با زمان‌بندی قابل تنظیم
- فلش‌کارت مفهومی و دستوری
- پرسش بازیابی قبل از نمایش پاسخ
- مرور تصویری و نقشه مفهومی
- صف مرور روزانه با حجم قابل کنترل
- ثبت پاسخ درست/نادرست و میزان اطمینان
- تشخیص موضوعات نیازمند تمرین مجدد
- امکان تعویق مرور با حفظ سابقه

زمان‌بندی اولیه می‌تواند ساده باشد و بعداً بر اساس عملکرد واقعی به الگوریتم پیشرفته‌تر ارتقا یابد. الگوریتم مرور باید نسخه‌بندی و قابل آزمون باشد.

## 12. ماژول دانش و آرشیو (Knowledge Base)

قابلیت‌ها:
- یادداشت مستقل یا مرتبط با درس
- خلاصه شخصی
- نکات کلیدی و دستورات
- دسته‌بندی و برچسب
- پیوند بین مفاهیم و منابع
- نقشه ذهنی و ارتباط مفاهیم در فاز بعدی
- جستجو و فیلتر
- خروجی Markdown و متن

موضوعات تکمیل‌شده می‌توانند به Knowledge تبدیل شوند و دوباره در مرور قرار گیرند.

## 13. آزمایشگاه و پروژه عملی

قابلیت‌ها:
- سناریوهای مرحله‌ای
- هدف و پیش‌نیاز
- توپولوژی/دیاگرام
- تجهیزات و سرویس‌های مورد نیاز
- دستورات و خروجی مورد انتظار
- مراحل اجرا و عیب‌یابی
- سؤال‌های بررسی فهم
- ثبت نتیجه و یادداشت کاربر
- سطح دشواری و زمان تخمینی

حوزه‌های محتوایی نمونه:
- شبکه، TCP/IP، subnetting، VLAN، routing و switching
- DNS، DHCP، Active Directory و Windows Server
- Linux، LPIC و مدیریت سرویس‌ها
- MikroTik و FortiGate
- VoIP، Asterisk و Issabel
- سرورهای HPE، iLO، RAID و Storage
- مجازی‌سازی، مانیتورینگ، امنیت و عیب‌یابی زیرساخت

## 14. گزارش‌ها و تحلیل پیشرفت

شاخص‌های پیشنهادی:
- زمان مطالعه و تمرین
- موضوعات شروع‌شده و تکمیل‌شده
- میزان موفقیت در آزمون‌ها
- موضوعات نیازمند مرور
- استمرار یادگیری، بدون تشویق به استفاده افراطی
- وضعیت کارهای روزانه
- روند شخصی در بازه‌های زمانی

گزارش‌ها توصیفی و کمک‌کننده باشند، نه قضاوتی. داده‌های Journal و افکار خصوصی نباید ناخواسته در گزارش‌های عمومی یا خروجی‌های اشتراکی ظاهر شوند.

## 15. جستجو، خروجی و پشتیبان‌گیری

- جستجوی یکپارچه با رعایت مجوز دسترسی و نوع داده
- خروجی Markdown و TXT برای یادداشت‌ها و دانش
- Backup کامل با نسخه schema، نسخه اپ و تاریخ ایجاد
- Restore با اعتبارسنجی فایل و نمایش نتیجه قبل از جایگزینی داده
- امکان انتخابی برای خروجی‌گرفتن از ماژول‌ها
- رمزنگاری فایل پشتیبان در صورت وجود داده حساس
- آزمون واقعی backup/restore در هر نسخه مهم
- نسخه پشتیبان قبل از Migrationهای پرریسک

## 16. همگام‌سازی و امنیت

مستند فعلی پروژه به ارتباط HTTP در شبکه محلی با برنامه ویندوز اشاره دارد. این ارتباط نباید بدون تغییرات امنیتی به اینترنت عمومی متصل شود.

الزامات:
- همگام‌سازی محتوای آموزشی از داده‌های شخصی جدا باشد.
- برای شبکه خارج از LAN، TLS، احراز هویت، مجوزدهی، اعتبارسنجی ورودی و مدیریت نشست لازم است.

- [ادغام MindRebuild و مشخصات پروفایل یادگیری شخصی](MINDREBUILD_INTEGRATION_AND_PERSONAL_LEARNING_PROFILE.md)

## 26. ممیزی تکمیلی Room و مرزبندی داده‌ها

## 27. Source reconstruction map and tracked-source divergence

The effective APK build uses a 38-step GitHub Actions workflow that extracts `MindUnlock-Android-v0.3.1-source.zip` into a temporary directory and applies many inline and compressed source transformations before Gradle runs. The checked-in `android/` tree is not the same source tree: the archive contains baseline Kotlin files such as `AppLock.kt`, `PersianSpeech.kt`, `StudyReminderReceiver.kt`, and `ui/StudyScreens.kt` that are absent from the tracked Android tree. The archive SHA-1 is `bb35cab525b86b2ed5136360985c96451c4daf16`; the workflow file is 154,656 characters and has 38 named steps.

**Architecture rule:** do not replace the checked-in Android tree with the ZIP baseline and do not remove CI patches until a disposable CI reconstruction reproduces the effective source and generates a per-file SHA-256 manifest. The detailed workflow inventory and current divergence are recorded in `docs/IMPLEMENTATION_AUDIT_AND_NEXT_STEPS.md`, section 10. Source stabilization is still pending; this finding does not mean the app source has been unified.

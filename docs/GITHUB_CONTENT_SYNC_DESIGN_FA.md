# طراحی اتصال GitHub و همگام‌سازی محتوا در MindUnlock

وضعیت: مرور عمومی، ورود Device Flow، ارسال امن Pull Request و واردسازی کنترل‌شده Manifest نسخه ۱ پیاده‌سازی شده‌اند؛ آزمون روی گوشی واقعی هنوز در انتظار است.
مخزن هدف: `MrUtility01/MindUnlock`
سطح مخزن: Public
شاخه پایه کد: `main`

## 1. هدف و اصول

اتصال GitHub یک منبع محتوای مستقل در کنار همگام‌سازی فعلی Windows است. قابلیت Windows حذف یا جایگزین نمی‌شود.

اصول:
- خواندن محتوای عمومی بدون ورود GitHub امکان‌پذیر باشد.
- هر عملیات نوشتن نیازمند ورود صریح کاربر و مجوز GitHub باشد.
- هیچ PAT، client secret یا کلید خصوصی در سورس یا APK قرار نگیرد.
- توکن‌ها در حافظه امن دستگاه نگهداری و هنگام خروج/لغو دسترسی پاک شوند.
- فایل قبل از واردشدن به پایگاه داده پیش‌نمایش شود.
- هیچ تعارضی به‌صورت خاموش با آخرین نسخه جایگزین نشود.
- تغییرات محتوایی از سورس برنامه جدا بمانند.
- همگام‌سازی با هش و شناسه نسخه انجام شود و گزارش قابل مشاهده داشته باشد.

## 2. مدل احراز هویت

### خواندن
برای مخزن عمومی، درخواست‌های GET به GitHub REST API بدون ورود انجام می‌شوند. محدودیت نرخ درخواست‌های ناشناس باید در رابط کاربری مدیریت شود؛ در صورت دریافت HTTP 403/429، برنامه زمان انتظار و امکان تلاش مجدد را نشان می‌دهد.

### نوشتن
برای بارگذاری، ایجاد commit یا Pull Request از GitHub App و OAuth Device Flow استفاده شود:
1. برنامه درخواست device code را به endpoint رسمی GitHub می‌فرستد.
2. کاربر کد یک‌بارمصرف را در مرورگر و صفحه رسمی GitHub تأیید می‌کند.
3. برنامه با polling کنترل‌شده access token کوتاه‌عمر/قابل لغو را دریافت می‌کند.
4. دسترسی GitHub App فقط به مخزن `MrUtility01/MindUnlock` محدود می‌شود.
5. مجوزهای App حداقلی باشند: Repository metadata = Read، Contents = Read & Write و Pull Requests = Read & Write؛ ساخت PR برای ارسال امن محتوا الزامی است.
6. پیش از هر عملیات نوشتن، مجوز و وضعیت نشست بررسی شود.

**پیش‌نیاز عملیاتی:** مالک مخزن باید GitHub App را بسازد، Device Flow را فعال کند، آن را فقط روی همین مخزن نصب کند و App Client ID را از مسیر امن پیکربندی build به برنامه بدهد. Client ID شناسه عمومی است، اما نباید client secret یا private key در APK قرار گیرد. تا زمان انجام این تنظیم در حساب مالک، ورود و نوشتن واقعی قابل فعال‌سازی نیست. برای خواندن مخزن عمومی نیازی به این تنظیم نیست.

توکن دریافتی باید با Android Keystore و رمزنگاری AES-GCM در فضای خصوصی برنامه ذخیره شود. اگر پیاده‌سازی رمزنگاری درون‌برنامه‌ای استفاده شد، کلید رمزنگاری هرگز در SharedPreferences یا فایل عادی ذخیره نشود. لاگ‌ها فقط نوع رخداد و شناسه درخواست را ثبت کنند و هرگز token، device code، کد تأیید یا هدر Authorization را ننویسند.

## 3. مرورگر مخزن و انتخاب فایل

ساختار صفحه:
- سربرگ مخزن و شاخه فعال؛ مقدار پیش‌فرض مخزن `MrUtility01/MindUnlock` و شاخه `main`.
- مرور پوشه‌ها با breadcrumb و امکان بازگشت.
- جست‌وجو بر اساس نام فایل.
- فیلتر نوع فایل: Markdown، JSON، متن، تصویر و سایر فایل‌های پشتیبانی‌شده.
- نمایش اندازه، آخرین commit و مسیر کامل.
- پیش‌نمایش قبل از دریافت یا واردسازی.
- انتخاب چند فایل فقط برای دانلود/واردسازی گروهی؛ انتخاب چندفایلی برای نوشتن باید مرحله تأیید جداگانه داشته باشد.

فایل‌های باینری بزرگ یا قالب‌های ناشناخته نباید به‌عنوان متن باز شوند. برای محتواهای آموزشی، فرمت‌های اولویت‌دار Markdown و JSON هستند. تصاویر/رسانه‌ها با کنترل اندازه، نوع MIME و SHA-256 دریافت شوند.

## 4. قرارداد محتوای MindUnlock

مسیر محتوای مدیریت‌شده:
- `content/library/` برای فایل‌های آموزشی.
- `content/manifest.json` برای فهرست نسخه‌دار محتوا.
- `content/inbox/` برای فایل‌های تازه بارگذاری‌شده و در انتظار بازبینی، در صورت نیاز به صف بررسی.

هر ورودی manifest حداقل شامل این فیلدها باشد:
- `id`: شناسه پایدار فصل/مطلب
- `title`: عنوان
- `group_name`: موضوع/دسته
- `order_num`: ترتیب فصل یا آیتم
- `path`: مسیر نسبی فایل
- `format`: نوع محتوا
- `content_hash`: SHA-256 محتوای نهایی
- `updated_at`: زمان UTC آخرین تغییر
- `schema_version`: نسخه قرارداد داده

برنامه باید با manifest نسخه‌دار کار کند و برای فیلدهای ناشناخته سازگار باشد. فایل نامعتبر یا manifest ناسازگار نباید در دیتابیس فعال شود.

### قرارداد اجرایی نسخه ۱

فایل فعال در مسیر `content/manifest.json` قرار می‌گیرد و آرایه `items` دارد. هر ورودی از فیلدهای بالا استفاده می‌کند. فایل‌های قابل واردسازی باید زیر `content/library/` باشند و فعلاً قالب‌های JSON فصل، Markdown و TXT پشتیبانی می‌شوند. برای JSON فصل، ساختار `chapter` و `items` با قرارداد موجود همگام‌سازی ویندوز سازگار است.

پیش از واردسازی، برنامه مسیر، شناسه‌های تکراری، نسخه schema، پسوند، اندازه و SHA-256 را بررسی می‌کند. وضعیت هر فصل به یکی از حالت‌های جدید، به‌روز، تغییر راه‌دور، تغییر محلی، تعارض دوطرفه یا محتوای محلی مدیریت‌نشده تبدیل می‌شود. فقط فصل جدید و تغییر راه‌دور بدون تغییر محلی قابل واردسازی خودکار هستند. نسخه‌های محلی، تعارض‌ها و شناسه‌های برخوردی بدون تأیید صریح جایگزین نمی‌شوند. حذف از Manifest نیز به‌تنهایی باعث حذف داده محلی نمی‌شود.

## 5. همگام‌سازی و نسخه‌بندی

برای هر فایل محلی، این اطلاعات نگهداری شود:
- repository، branch و path
- آخرین commit SHA مشاهده‌شده
- blob SHA فایل دریافت‌شده
- SHA-256 محتوای محلی
- زمان آخرین همگام‌سازی
- وضعیت: همگام، محلیِ تغییرکرده، راه‌دورِ تغییرکرده، تعارض، یا خطا

چرخه دریافت:
1. دریافت manifest و شاخه/commit مرجع.
2. مقایسه SHA و content_hash با نسخه محلی.
3. دانلود فقط فایل‌های جدید یا تغییرکرده.
4. اعتبارسنجی نوع، اندازه، schema و hash.
5. نمایش خلاصه تغییرات و درخواست تأیید برای واردسازی.
6. اعمال همه تغییرات یک فصل در تراکنش پایگاه داده.
7. ثبت گزارش نتیجه و زمان.

چرخه ارسال:
1. بررسی مجوز Contents و نشست معتبر.
2. انتخاب فایل و مسیر مجاز در `content/inbox/` یا `content/library/`.
3. بررسی اندازه، پسوند، UTF-8 و عدم وجود اطلاعات محرمانه.
4. مقایسه نسخه مبنا با HEAD راه‌دور.
5. ارسال تغییر به شاخه اختصاصی محتوا، نه شاخه اصلی کد.
6. ساخت Pull Request برای بازبینی و ادغام؛ هیچ force-push یا بازنویسی اجباری مجاز نیست.

## 6. مدیریت تعارض

تعارض وقتی رخ می‌دهد که فایل از زمان آخرین همگام‌سازی هم در دستگاه و هم در GitHub تغییر کرده باشد.

رفتار:
- نسخه محلی، نسخه مبنا و نسخه راه‌دور حفظ شوند.
- هیچ نسخه‌ای بدون انتخاب صریح کاربر حذف یا جایگزین نشود.
- برای متن‌های UTF-8، diff سه‌طرفه نمایش داده شود.
- اگر تغییرها در خطوط/بخش‌های مستقل باشند، پیشنهاد ادغام خودکار فقط پس از پیش‌نمایش و تأیید کاربر ارائه شود.
- اگر تغییرها هم‌پوشان باشند یا فایل JSON/ساختاریافته ناسازگار شود، ادغام خودکار ممنوع و انتخاب دستی لازم است.
- گزینه‌ها: نگه‌داشتن محلی، دریافت نسخه راه‌دور، ویرایش/ادغام دستی، یا ذخیره هر دو نسخه با نام تعارض.
- پس از حل تعارض، hash و commit SHA جدید ثبت شود.

خطای HTTP 409، 422 یا تغییر SHA هنگام ارسال باید به‌عنوان تعارض/نسخه کهنه تفسیر شود؛ برنامه نباید بی‌درنگ همان PUT را تکرار کند.

## 7. جداسازی از همگام‌سازی Windows

هر دو منبع در صفحه «منابع محتوا» به‌صورت مستقل نمایش داده شوند:
- Windows LAN: ورود با حساب برنامه Windows و API فعلی.
- GitHub Public: خواندن عمومی، و در صورت پیکربندی GitHub App ورود برای نوشتن.

هر منبع تنظیمات، آخرین همگام‌سازی، وضعیت اتصال، گزارش خطا و manifest مستقل دارد. شناسه منبع باید همراه شناسه فصل ذخیره شود تا فصل‌های هم‌نام از دو منبع روی هم نوشته نشوند.

## 8. امنیت و حریم خصوصی

- درخواست‌ها فقط HTTPS؛ redirect به HTTP رد شود.
- مجاز بودن host به `api.github.com` و دامنه‌های رسمی محتوای GitHub محدود شود.
- مسیر فایل normalize شود؛ مسیرهای absolute، `..`، کنترل‌کاراکترها و symlink خارج از ریشه رد شوند.
- محدودیت اندازه برای فایل‌های متنی و رسانه‌ای اعمال شود.
- محتوا پیش از parse از نظر ساختار و حجم بررسی شود.
- محتوای دریافتی از مخزن داده غیرقابل اعتماد است؛ هیچ script یا فرمانی از آن اجرا نشود.
- توکن در Crash report، analytics، exception message و DownloadAuditLog ظاهر نشود.
- دکمه «قطع اتصال GitHub» توکن ذخیره‌شده را پاک کند.
- دسترسی عمومی مخزن به معنی اجازه نوشتن برای همه نیست؛ فقط مالک/همکار یا کاربری که GitHub App برایش مجوز صادر کرده می‌تواند ارسال کند.

## 9. آزمون‌های پذیرش

1. خواندن manifest و فایل از مخزن عمومی بدون ورود.
2. مرور پوشه، انتخاب فایل، پیش‌نمایش و دانلود فایل UTF-8.
3. رفتار درست در rate limit و قطع اینترنت.
4. ورود Device Flow با کد منقضی، رد مجوز، لغو و توکن نامعتبر.
5. عدم وجود token/device code در لاگ‌ها.
6. رد مسیر traversal و فایل با اندازه/نوع نامعتبر.
7. تشخیص فایل جدید، حذف‌شده و تغییرکرده.
8. رد بازنویسی در صورت stale blob SHA یا HTTP 409.
9. حل تعارض بدون از دست رفتن نسخه محلی یا راه‌دور.
10. عدم تداخل داده‌های GitHub با Windows sync.
11. تست migration دیتابیس و حفظ رکوردهای موجود.
12. تست UI روی اندازه نمایشگر کوچک و زبان RTL.

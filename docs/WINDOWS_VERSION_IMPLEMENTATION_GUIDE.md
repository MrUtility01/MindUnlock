# راهنمای جامع طراحی و پیاده‌سازی نسخه Windows — MindUnlock

> وضعیت: مشخصات مصوب برای برنامه‌ریزی توسعه نسخه Windows؛ نه گزارش قابلیت‌های پیاده‌سازی‌شده.
> محصول نهایی: MindUnlock. این نسخه باید هم‌سطح نسخه Android و هم‌راستا با مشخصات ادغام MindRebuild باشد.
> اصل مهم: هیچ قابلیت این سند تا زمان وجود کد، تست و نسخه قابل نصب، «پیاده‌سازی‌شده» محسوب نمی‌شود.

## 1. هدف و دامنه

ساخت نسخه دسکتاپ Windows برای Windows 10/11 x64، با تجربه فارسی و راست‌به‌چپ، آفلاین‌محور، امن و قابل استفاده بدون حساب کاربری یا اینترنت. نسخه Windows باید تمام قابلیت‌های موجود Android را پوشش دهد و تمام ماژول‌های مصوب MindRebuild/MindUnlock را نیز به‌صورت کامل در نقشه توسعه داشته باشد.

نسخه Windows یک محصول مستقل با داده‌های محلی خودش است؛ نباید مستقیماً فایل دیتابیس Android را باز کند یا هم‌زمان روی یک فایل SQLite مشترک بنویسد. تبادل اطلاعات فقط از مسیر Import/Export یا سرویس Sync نسخه‌بندی‌شده انجام می‌شود.

## 2. اصول غیرقابل مذاکره

1. Offline-first و Local-first: امکانات اصلی بدون اینترنت و ثبت‌نام کار کنند.
2. Persian-first: رابط فارسی RTL، فونت مناسب فارسی، اعداد و تاریخ قابل تنظیم و تقویم شمسی.
3. Privacy by design: افکار، ژورنال، یادداشت‌ها و برنامه‌های شخصی به‌صورت پیش‌فرض محلی بمانند.
4. عدم اجبار به Cloud: هیچ حساب یا سرور ابری برای استفاده پایه لازم نباشد.
5. داده قابل انتقال: Backup/Restore و Import/Export مستند، نسخه‌بندی‌شده و آزمون‌شده.
6. توسعه‌پذیری: مرزهای ماژول‌ها و مدل داده مستقل از UI باشند.
7. هم‌ترازی قابلیت‌ها: فهرست قابلیت‌ها بین Android و Windows با شناسه و وضعیت مشترک نگهداری شود.
8. دسترس‌پذیری: پشتیبانی از صفحه‌کلید، مقیاس‌بندی DPI، اندازه متن، کنتراست و Screen Reader.
9. عدم ادعای تکمیل: موفقیت Build به معنی صحت رفتار یا تکمیل قابلیت نیست.

## 3. فناوری پیشنهادی

### گزینه پیشنهادی: Kotlin + Compose Multiplatform Desktop

با توجه به اینکه نسخه Android با Kotlin و Jetpack Compose ساخته شده، مسیر کم‌هزینه‌تر این است که منطق دامنه و در صورت امکان UI مشترک به Kotlin Multiplatform منتقل شود و رابط دسکتاپ با Compose Multiplatform ساخته شود.

- زبان: Kotlin
- UI دسکتاپ: Compose Multiplatform Desktop
- معماری: Clean Architecture سبک + MVVM/Unidirectional Data Flow
- DI: انتخاب یک راهکار ساده و مشترک پس از ارزیابی وابستگی‌های فعلی
- پایگاه داده Windows: SQLite با لایه Repository و Migration نسخه‌بندی‌شده؛ انتخاب Room KMP یا SQLDelight فقط پس از Proof of Concept و بررسی پشتیبانی نسخه‌ها
- تنظیمات و فایل‌ها: مسیرهای استاندارد Windows از طریق APIهای سیستم؛ نه مسیر ثابت و نه ذخیره در پوشه نصب برنامه
- بسته‌بندی: ابتدا MSI یا MSIX؛ انتخاب نهایی بر اساس نصب per-user/per-machine، امضای کد و روش به‌روزرسانی
- تست: Kotlin/JVM unit tests، integration tests دیتابیس، UI tests و تست نصب/ارتقا روی Windows 10/11

**ممنوع:** شروع با بازنویسی کامل Android یا تغییر فوری دیتابیس فعلی. ابتدا تثبیت منبع Android، تعریف قراردادهای دامنه و اجرای نمونه فنی دسکتاپ انجام شود.

### ساختار مخزن پیشنهادی

```
MindUnlock/
  android/                 # برنامه Android؛ پس از تثبیت سورس اصلی
  desktop/

  shared/

    learning/               # موتور یادگیری و مرور
    data/                   # Repository interfaces و mapping
    backup/                 # فرمت پشتیبان و اعتبارسنجی

```

این ساختار هدف معماری است؛ نباید تا پیش از ممیزی وابستگی‌ها به‌صورت مکانیکی ساخته شود. ماژول‌ها را مرحله‌ای استخراج کنید.

## 4. قابلیت‌های الزامی نسخه Windows

### 4.1 مدیریت ذهن و زندگی روزمره

- Mind Dump / Inbox: ثبت سریع افکار، کارهای ناگهانی و موارد باز؛ دسته‌بندی، تبدیل به Task یا موضوع یادگیری و بایگانی.
- Tasks: وظایف، اولویت، موعد، وضعیت، برچسب، یادآور و ارتباط با موضوع یا پروژه.
- Daily Plan: برنامه روزانه با امکان انتقال موارد انجام‌نشده بدون ایجاد حس عقب‌ماندگی.
- Journal: دفتر روزانه خصوصی با تاریخ شمسی/میلادی، جست‌وجو و پیوست اختیاری.
- Later / Future Topics: فهرست موضوعاتی که فعلاً زمان یادگیری آن‌ها نیست.
- Curiosity: سؤال‌ها و کنجکاوی‌های جانبی با امکان تبدیل به موضوع مستقل.
- Knowledge Archive: ذخیره خلاصه‌ها، نکته‌ها، منابع و ارتباط بین مفاهیم.
- Reports: گزارش ساده و قابل فهم از روند مطالعه، جلسات، تمرین‌ها و وظایف؛ بدون قضاوت یا امتیازدهی تنبیهی.
- Quotes & Techniques: نقل‌قول‌ها، روش‌ها و تکنیک‌های شخصی با جست‌وجو و دسته‌بندی.

### 4.2 موتور یادگیری

هر موضوع از مسیر قابل تنظیم زیر پشتیبانی کند:
1. چرا این موضوع مهم است؟
2. تصویر کلی و کاربرد
3. معماری و اجزای اصلی
4. ارتباط اجزا با یکدیگر
5. جزئیات و اصطلاحات
6. مثال‌های واقعی
7. کاربرد در محیط کار
8. آزمایشگاه و تمرین عملی
9. پرسش و پاسخ و بازیابی فعال
10. توضیح مطلب با زبان خود کاربر (Teach-back)
11. خلاصه تصویری و نقشه ذهنی
12. برنامه مرور بعدی

قواعد:
- حداکثر دو موضوع یادگیری فعال به‌صورت پیش‌فرض؛ قابل تغییر در تنظیمات.
- جلسه پیش‌فرض ۳۰ دقیقه: ۱۰ دقیقه آموزش، ۱۵ دقیقه تمرین، ۵ دقیقه جمع‌بندی؛ زمان قابل تنظیم.
- حالت روز کم‌انرژی با جلسه کوتاه‌تر.
- هر پاسخ اشتباه باید دلیل خطا و پاسخ/روش اصلاح را توضیح دهد.
- سؤال جانبی سه وضعیت داشته باشد: ضروری (پاسخ همین حالا)، موکول‌شده، کنجکاوی.
- مرور مفهومی (چرایی، معماری، ارتباط‌ها و کاربرد) از مرور جزئیات (دستورها، پارامترها، مسیرها و مراحل) جدا باشد.
- Flashcards، Active Recall، Spaced Repetition، مرور دستورهای آزمایشگاه و ثبت علت خطا پشتیبانی شوند.
- در بازگشت پس از وقفه، فقط آخرین موضوع، آخرین مرحله، خلاصه قبلی، یک پرسش یادآوری و دقیقاً یک گام بعدی نمایش داده شود.
- قبل از شروع جلسه امکان تخلیه ذهن به Inbox باشد و کاربر بدون از دست دادن جای درس به آن بازگردد.

### 4.3 پروفایل یادگیری شخصی

پروفایل باید قابل ویرایش، قابل بازنشانی و مبتنی بر شواهد باشد؛ کاربر به یک «سبک یادگیری ثابت» برچسب نخورد.

تنظیمات قابل ثبت:
- شیوه ارائه: تصویر، نمودار، توضیح معلم‌گونه، مثال.
- ترتیب: نمای کلی، معماری، ارتباط اجزا، جزئیات.
- تمرین: عملی، آزمایشگاه، سناریوی واقعی.
- مرور: نقشه ذهنی، خلاصه تصویری، بازیابی فعال.
- موانع تمرکز: شلوغی ذهن، موضوعات حل‌نشده، حواس‌پرتی.
- ساختار: گام بعدی روشن، ادامه پس از وقفه.
- علاقه و ارتباط بین موضوعات.

ترجیحی که کاربر اعلام می‌کند از عملکردی که سیستم مشاهده می‌کند جدا ذخیره شود. تغییر پروفایل تدریجی باشد و توضیح دهد بر چه شواهدی تکیه کرده است. دو حالت Guided و Flexible ارائه شود.

### 4.4 قابلیت‌های فعلی Android که باید در Windows حفظ شوند

پیش از شروع توسعه، موجودی واقعی کد Android با این فهرست تطبیق داده شود؛ موارد زیر در ممیزی فعلی مشاهده شده‌اند و باید حفظ/معادل‌سازی شوند:
- کتابخانه محتوا، فصل‌ها و آیتم‌های آموزشی
- Reader و ادامه مطالعه
- دریافت/ذخیره آفلاین محتوا
- فلش‌کارت و مرور زمان‌بندی‌شده
- Quiz / Exam
- Progress و گزارش مطالعه
- Notes و Bookmarks
- Planner / Study Tasks و یادآورها
- تنظیمات برنامه و تنظیمات مطالعه
- قفل محلی برنامه
- گفتار فارسی (در Windows با انتخاب موتور TTS سازگار و امکان غیرفعال‌سازی)
- تشخیص/گزارش خطا و ابزار عیب‌یابی
- همگام‌سازی محتوا با سرویس خودمیزبان، پس از ایمن‌سازی پروتکل

وجود قابلیت در Android به معنی کامل بودن آن یا آماده بودن انتقال نیست؛ هر مورد باید در جدول Feature Parity وضعیت مستقل داشته باشد.

## 5. تجربه کاربری دسکتاپ

- صفحه اصلی با Navigation واضح: داشبورد، Inbox، یادگیری، برنامه‌ریزی، ژورنال، دانش، مرور، گزارش و تنظیمات.
- پنجره قابل تغییر اندازه و پشتیبانی از نمایشگر کوچک و بزرگ.
- Layout دسکتاپ: نوار کناری قابل جمع‌شدن، پنل محتوا و پنل جزئیات اختیاری.
- میانبرهای صفحه‌کلید برای ثبت سریع Inbox، جست‌وجو، شروع/توقف جلسه، ذخیره و بازگشت.
- جست‌وجوی سراسری در عنوان، متن، یادداشت، ژورنال، منابع و موضوع‌ها؛ با فیلتر نوع و تاریخ.
- Drag & Drop برای پیوست فایل و مرتب‌سازی در مواردی که معنا دارد.
- اعلان‌های Windows برای یادآورها با رضایت کاربر و تنظیم جداگانه.
- Auto-save برای متن‌های بلند، نشانگر ذخیره و بازیابی پس از Crash.
- رابط RTL واقعی، نه صرفاً راست‌چین کردن متن؛ ترتیب فوکوس، منو، آیکن‌های جهت‌دار و جدول‌ها نیز باید درست باشند.
- پشتیبانی از فونت فارسی، مقیاس DPI، چند نمایشگر و حالت روشن/تیره.

## 6. داده، پایگاه داده و مهاجرت

### 6.1 مدل داده مشترک هدف

مدل‌های دامنه باید دست‌کم این موجودیت‌ها را پوشش دهند:
- InboxItem, Task, DailyPlan, JournalEntry
- LearningTopic, FutureTopic, CuriosityItem, KnowledgeEntry
- Quote, Technique
- LearningProfile, LearningProfileAnswer, LearningProfileObservation
- LearningSession, LearningSessionFeedback
- LearningQuestion, LearningQuestionLink
- ReviewItem, ReviewAttempt
- ContentChapter, ContentItem, Progress, Note, Bookmark
- Attachment, Reminder, SyncMetadata, MigrationMetadata

برای هر موجودیت: شناسه پایدار، زمان ایجاد/ویرایش، حذف نرم در صورت نیاز، منبع تغییر و نسخه Schema تعریف شود. داده خصوصی از محتوای آموزشی قابل انتشار جدا باشد.

### 6.2 قواعد دیتابیس

- از یک فایل دیتابیس محلی برای هر نصب Windows استفاده شود؛ محل آن در AppData کاربر باشد.
- هر Migration نسخه مشخص، مسیر ارتقا، مسیر شکست و تست رفت‌وبرگشت داده داشته باشد.
- قبل از Migration مخرب، Backup خودکار ایجاد و صحت آن بررسی شود.
- تراکنش‌ها و عملیات چندمرحله‌ای با وضعیت قابل بازیابی طراحی شوند.
- شمارش ردیف‌ها، کلیدها و داده‌های حیاتی بعد از مهاجرت کنترل شود.
- دیتابیس قدیمی تا پایان اعتبارسنجی حذف نشود.
- رمزنگاری دیتابیس یا حداقل رمزنگاری Backup با کلید محافظت‌شده توسط Windows DPAPI بررسی و طراحی شود؛ رمز عبور خام در فایل تنظیمات ذخیره نشود.
- هیچ فایل دیتابیس Android مستقیماً توسط Windows باز نشود.

### 6.3 مهاجرت از Android

مسیر رسمی انتقال:
1. Android یک Backup استاندارد و نسخه‌بندی‌شده تولید کند.
2. کاربر فایل را به Windows منتقل کند.
3. Windows فایل، نسخه، امضا/هش، ساختار و فضای موردنیاز را اعتبارسنجی کند.
4. پیش‌نمایش تعداد رکوردها و دسته‌های قابل واردکردن نشان داده شود.
5. Import ابتدا در فضای موقت انجام شود.
6. صحت تعداد، شناسه‌ها و ارتباط رکوردها کنترل شود.
7. فقط پس از تأیید، داده‌ها در دیتابیس اصلی ثبت شوند.
8. گزارش نتیجه و امکان بازگردانی ارائه شود.

## 7. همگام‌سازی Android و Windows

Sync اختیاری است و نباید شرط استفاده از برنامه باشد.

- نسخه اول: انتقال دستی با Backup/Restore.
- نسخه بعدی: Sync در شبکه محلی از طریق HTTPS/TLS یا کانال امن معادل.
- هر دستگاه شناسه مستقل داشته باشد.
- Sync باید idempotent، قابل ادامه پس از قطع اتصال و دارای گزارش تعارض باشد.
- حذف‌ها با Tombstone/soft-delete منتقل شوند تا داده حذف‌شده دوباره برنگردد.
- تعارض‌ها بر اساس نوع داده حل شوند؛ برای ژورنال و یادداشت، بازنویسی خاموش ممنوع و نسخه‌های دوگانه قابل بازیابی باشند.
- هیچ رمز عبور یا توکن در Log ثبت نشود.
- HTTP cleartext فعلی نباید برای تبادل داده حساس Windows/Android استفاده شود.
- Cloud Sync در دامنه نسخه اولیه نیست؛ فقط پس از تصمیم محصول، مدل تهدید و طراحی حریم خصوصی اضافه شود.

## 8. امنیت و حریم خصوصی

- نصب و به‌روزرسانی از بسته امضاشده و ناشر قابل تشخیص.
- حداقل دسترسی سیستم؛ عدم نیاز به Administrator برای نصب per-user در صورت امکان.
- نگهداری اسرار در Windows Credential Manager یا DPAPI.
- قفل برنامه اختیاری با زمان قفل و رفتار بازیابی روشن؛ قفل UI جایگزین رمزنگاری داده نیست.
- عدم ارسال Telemetry شخصی به‌صورت پیش‌فرض.
- Crash log بدون متن ژورنال، یادداشت، رمز یا محتوای شخصی.
- کاربر بتواند Log را قبل از ارسال بازبینی کند.
- ارتباط شبکه با TLS، اعتبارسنجی گواهی و مدیریت امن Token.
- سیاست روشن برای داده‌های محلی، Backup، حذف و Sync.
- مسیرهای فایل و ورودی‌های Import در برابر Path Traversal و فایل‌های مخرب اعتبارسنجی شوند.

## 9. Backup / Restore و خروجی داده

- Backup کامل و انتخابی: همه داده‌ها یا فقط داده‌های انتخاب‌شده.
- فرمت نسخه‌بندی‌شده و مستقل از فرمت داخلی SQLite؛ ترجیحاً بسته ZIP شامل manifest، JSON/SQLite export و فایل‌های پیوست.
- امکان رمزگذاری Backup با گذرواژه کاربر و KDF استاندارد.
- Manifest شامل نسخه برنامه، نسخه Schema، تاریخ، تعداد رکوردها، هش فایل‌ها و فهرست پیوست‌ها.
- Restore ابتدا در محیط موقت و پس از اعتبارسنجی انجام شود.
- پیش از Restore، Backup خودکار از وضعیت فعلی ساخته شود.
- Export داده‌های قابل خواندن مانند Markdown/CSV/JSON برای جلوگیری از قفل‌شدن کاربر در محصول.
- تست بازیابی روی نصب تمیز و روی نسخه ارتقایافته اجباری است.

## 10. دسترسی‌پذیری و کیفیت

- کارکرد کامل با صفحه‌کلید و ترتیب Tab منطقی.
- نام قابل خواندن برای کنترل‌ها و پشتیبانی Screen Reader.
- مقیاس‌بندی 100 تا 200 درصد و نمایش صحیح روی DPIهای مختلف.
- کنتراست مناسب، عدم اتکا به رنگ تنها برای نمایش وضعیت.
- پشتیبانی از کاهش حرکت/انیمیشن در صورت نیاز.
- ذخیره خودکار و بازیابی Draftها پس از Crash.
- کارکرد صحیح تاریخ شمسی، ساعت محلی، تغییر منطقه زمانی و مرز روز.
- عملکرد مناسب روی سخت‌افزار میان‌رده و دیتابیس بزرگ.

## 11. برنامه اجرایی مرحله‌ای

### فاز 0 — تثبیت مرجع Android
خروجی: سورس Android قابل بازسازی، فهرست Patchها، وضعیت واقعی قابلیت‌ها، Schemaهای مستند و ریسک‌های Migration.
معیار پذیرش: Build از سورس tracked بدون Patch پنهان انجام شود؛ هیچ داده‌ای در فرایند حذف نشود.

### فاز 1 — اثبات فنی Windows
خروجی: برنامه آزمایشی Compose Desktop که روی Windows 10/11 اجرا شود، RTL، فونت، تاریخ شمسی، ذخیره SQLite و بسته نصب را اثبات کند.
معیار پذیرش: نصب/حذف/ارتقا، اجرای آفلاین، مسیر داده per-user و بازگشایی دیتابیس موفق باشد.

### فاز 2 — هسته مشترک
خروجی: مدل‌های دامنه، Use Caseها، Repository contracts، خطاها، تاریخ/زمان و اعتبارسنجی مشترک.
معیار پذیرش: تست‌های واحد مستقل از UI؛ عدم وابستگی Domain به Compose یا Android APIs.

### فاز 3 — امکانات پایه دسکتاپ
ترتیب: Dashboard، Inbox، Tasks، Daily Plan، Journal، جست‌وجو، Notes و Knowledge Archive.
معیار پذیرش: ذخیره پایدار، Auto-save، جست‌وجو و Backup/Restore برای همه این داده‌ها.

### فاز 4 — موتور یادگیری
ترتیب: Learning Topics، Guided/Flexible، جلسات، پرسش و پاسخ، Teach-back، پروفایل یادگیری، فلش‌کارت و مرور فاصله‌دار.
معیار پذیرش: چرخه کامل یادگیری بدون اینترنت و با Resume پس از قطع/بستن برنامه.

### فاز 5 — برابری قابلیت با Android
Reader، محتوا، دانلود آفلاین، Quiz/Exam، Progress، Bookmarks، Study Tasks، یادآورها، TTS و ابزار عیب‌یابی.
معیار پذیرش: جدول Feature Parity با تست و مدرک برای هر مورد.

### فاز 6 — انتقال و همگام‌سازی
ابتدا Import/Export استاندارد؛ سپس Sync شبکه محلی امن.
معیار پذیرش: آزمون تعارض، قطع اتصال، تکرار Sync، حذف و بازیابی.

### فاز 7 — انتشار عمومی
امضای کد، نصب‌کننده، به‌روزرسانی امن، سیاست حریم خصوصی، راهنمای فارسی، گزارش خطا و کانال انتشار.
معیار پذیرش: نصب تمیز و ارتقا روی Windows 10/11 x64، امضای معتبر، تست آفلاین و Backup/Restore موفق.

## 12. جدول Feature Parity

برای هر قابلیت یک ردیف با این ستون‌ها نگهداری شود:
- Feature ID
- نام قابلیت
- وضعیت Android
- وضعیت Windows
- مدل داده
- Offline verified
- Unit/Integration/UI test
- Backup/Restore verified
- Sync verified (اگر مرتبط)
- نسخه و لینک شواهد

وضعیت‌های مجاز: Planned، In Progress، Implemented، Tested، Released، Blocked. واژه Implemented بدون تست کافی نیست؛ Released فقط پس از انتشار واقعی.

## 13. تست‌های اجباری پیش از انتشار

1. نصب تمیز، ارتقا از نسخه قبلی، حذف و نصب مجدد بدون حذف ناخواسته داده.
2. اجرای کامل آفلاین و عدم وابستگی به سرویس شبکه.
3. تست RTL، فونت، اعداد، تاریخ شمسی، ساعت تابستانی/منطقه زمانی.
4. تست ایجاد/ویرایش/حذف/جست‌وجوی همه انواع داده.
5. بستن اجباری برنامه حین ذخیره و بازیابی Draft.
6. Backup، تغییر داده، Restore و تطبیق تعداد و شناسه رکوردها.
7. Import از Android با فایل سالم، خراب، ناقص، نسخه جدیدتر و نسخه قدیمی‌تر.
8. تست دیتابیس بزرگ، پیوست‌های حجیم و فضای دیسک کم.
9. تست Sync با قطع شبکه، تکرار درخواست، تعارض هم‌زمان و حذف.
10. تست مجوزها، ذخیره اسرار، TLS و عدم ثبت اطلاعات شخصی در Log.
11. تست صفحه‌کلید، Screen Reader، DPI و چند نمایشگر.
12. تست روی Windows 10 و Windows 11 در ماشین واقعی یا VM؛ Build موفق به‌تنهایی کافی نیست.

## 14. مواردی که نباید انجام شوند

- کپی مستقیم دیتابیس Android به Windows و استفاده مشترک از یک فایل.
- بازنویسی کامل Android هم‌زمان با شروع Windows.
- ساخت قابلیت Cloud اجباری یا حساب کاربری اجباری.
- انتقال Migration قدیمی بدون شناخت نسخه و تست.
- استفاده از HTTP برای ارسال داده شخصی یا اطلاعات ورود.
- ذخیره کلید/رمز خام در فایل تنظیمات یا Log.
- ادعای تکمیل قابلیت صرفاً بر اساس ظاهر UI یا موفقیت Build.
- انتشار نسخه عمومی قبل از Backup/Restore و تست ارتقا.

## 15. نخستین کارهای قابل اجرا

1. ایجاد Issue یا Epic با عنوان Windows Desktop Edition.
2. تثبیت سورس Android و ثبت نسخه مرجع.
3. ساخت Feature Parity Matrix از قابلیت‌های واقعی Android و نیازمندی‌های مصوب.
4. اجرای Proof of Concept برای Compose Multiplatform روی Windows 10/11.
5. آزمون RTL فارسی، Jalali، SQLite و بسته‌بندی MSI/MSIX.
6. تصمیم معماری مستند (ADR) برای اشتراک Domain، دیتابیس و Sync.
7. شروع فاز هسته مشترک فقط پس از موفقیت Proof of Concept.

## 16. معیار نهایی تحویل نسخه Windows

نسخه Windows زمانی قابل تحویل است که:
- همه قابلیت‌های مصوب در ماتریس برابری وضعیت Released یا استثنای مستند داشته باشند.
- برنامه بدون اینترنت برای قابلیت‌های اصلی کامل کار کند.
- داده‌ها محلی، خصوصی و قابل پشتیبان‌گیری باشند.
- Backup/Restore و Import از Android با تطبیق داده اثبات شده باشند.
- هیچ Migration یا Sync مخرب و بدون گزارش وجود نداشته باشد.
- نصب، ارتقا و اجرای Windows 10/11 آزمون شده باشد.
- تست‌های واحد، یکپارچه، UI و پذیرش اجرا شده و گزارش آن‌ها در مخزن ثبت شده باشد.
- راهنمای فارسی نصب، استفاده، انتقال داده و عیب‌یابی آماده باشد.

---
**تصمیم اجرایی:** نسخه Windows بخشی از محصول MindUnlock است، نه محصول جداگانه. تمام قابلیت‌های MindRebuild در همین محصول ادغام می‌شوند. توسعه Windows باید پس از تثبیت منبع Android و با هسته دامنه قابل اشتراک آغاز شود؛ اما طراحی و Proof of Concept دسکتاپ می‌تواند به‌صورت شاخه مستقل و بدون دست‌کاری دیتابیس فعلی شروع شود.
